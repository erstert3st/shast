# shast

A terminal typing game for real shell commands. You get a command a DevOps or
backend engineer actually uses, type it as fast and accurately as you can, and
on an exact match it runs inside an isolated Docker sandbox. Its output
streams live into the TUI, just like in a real terminal, followed by the exit
code, the run time and a short explanation of what the command did.

```
Round 3/10 · text · medium

  awk '{print $1}' logs/access.log | sort | uniq -c | sort -rn | head -5

WPM  61 · Accuracy 97% · Errors 2 · 9.8s
── output ──────────────────────────────────────────────────────────────────────
     80 45.33.12.8
     79 203.0.113.7
     57 192.168.1.23
     41 198.51.100.14
     33 10.0.5.40
────────────────────────────────────────────────────────────────────────────────
exit 0 · 0.03s
Counts requests per client IP and shows the five busiest. The classic sort |
uniq -c | sort -rn pipeline.
enter next round · ↑/↓ pgup/pgdn scroll · ctrl+c quit
```

## Prerequisites

- Go 1.27 or newer (to build; the result is a single binary)
- Docker Engine, reachable by your user (`docker ps` works without sudo, e.g.
  by being in the `docker` group). `DOCKER_HOST` and friends are honoured.
- A terminal of at least 60x16; the game is designed for 80x24.
- Building the sandbox image needs network access once (Debian packages).

## Build and run

```sh
make build              # or: go build -o shast .
./shast image build     # builds the sandbox image (once, ~1 min)
./shast                 # play
```

If Docker is not reachable or the image is missing (or outdated after an
update of shast), `shast` stops with a clear message before the UI starts.

### Playing

The setup screen lets you pick the difficulty (all/easy/medium/hard), the
category, the number of rounds and the order (`random` or by `difficulty`).
All of it can be preselected with flags:

```sh
./shast --difficulty medium --category text --rounds 5 --order difficulty --seed 42
```

| Flag | Meaning |
|---|---|
| `--difficulty` | `all`, `easy`, `medium`, `hard` |
| `--category` | `all`, `files`, `search`, `text`, `json`, `archive`, `git`, `permissions`, `disk`, `process`, `network-config`, `system` |
| `--rounds` | rounds per session (default 10) |
| `--order` | `random` (no repeats) or `difficulty` (easy → hard, random within a level) |
| `--seed` | makes the order reproducible |
| `--catalog DIR` | additional commands, see below |
| `--timeout` | per-command timeout (default 10s) |

Keys while typing: characters are checked one by one (green = correct,
red = wrong, grey = pending). You may type on after a mistake and fix it with
Backspace. **Enter only runs the command on an exact match.** Esc skips the
round, Ctrl+C quits. While the command runs, ↑/↓/PgUp/PgDn scroll the output
and Esc stops the command (the round still counts); Enter continues to the
next round.

Scoring: the timer starts with your first keystroke and stops with Enter.
WPM = (characters / 5) / minutes, accuracy = correct keystrokes / all
keystrokes (corrected mistakes still count), errors = wrong keystrokes. The
session score is WPM × accuracy; the top 10 are stored in
`$XDG_DATA_HOME/shast/scores.json` (default `~/.local/share/shast/`) together
with the chosen filters. Skipped rounds do not count towards the statistics,
so only sessions without skipped rounds enter the highscores.

## The sandbox

Every session starts one container from the `shast-sandbox` image (Debian
trixie-slim with coreutils, findutils, grep, sed, gawk, jq, tar, gzip, xz,
zip, git, procps, tree, file, bc, util-linux, diffutils, column):

- no network, runs as the unprivileged user `dev`, all capabilities dropped,
  `no-new-privileges`, no setuid binaries, read-only root filesystem
- limits: 128 processes, 256 MiB memory (no swap), 1 CPU, per-command timeout,
  1 MiB output per command, no IPC/shared memory, no core dumps
- the workspace `/work` is reset to the pristine seed before every command, so
  destructive commands (`rm -rf`, `find -delete`, `sed -i`, `chmod 000`) are
  safe; leftover processes are killed after every command
- the container is removed when shast exits, including Ctrl+C and signals. If
  shast is killed hard, the next start removes the orphan, and a watchdog
  removes it after four hours at the latest.

The seed in `/work` is a small fake project "shopapi": nginx and app configs,
access/app/error logs (plus rotated `.gz`), CSV/JSON data, a git repository
with a short history, cache files of different sizes, secrets with mode 600
and scripts with mode 755. It is generated by
[`internal/sandbox/image/seed.sh`](internal/sandbox/image/seed.sh) without any
randomness: fixed timezone (UTC), locale (C.UTF-8), hostname (`web01`), user,
file contents, mtimes and git dates. The image tag is a hash of the build
context, so a changed seed always means a new tag.

## Adding commands

Commands live in [`internal/catalog/commands.yaml`](internal/catalog/commands.yaml)
(embedded in the binary). Adding one needs no code change:

```yaml
- id: top-client-ips            # unique, [a-z0-9-]
  command: |-                   # printable ASCII, one line, max 120 chars
    awk '{print $1}' logs/access.log | sort | uniq -c | sort -rn | head -5
  category: text                # one of the categories above
  difficulty: medium            # easy | medium | hard
  explanation: "Counts requests per client IP and shows the five busiest."
  deterministic: true           # optional (default true); false for ps, date, …
  compare: { ignore_order: true } # optional: output line order is not stable
  exit_code: 0                  # optional: expected exit code (default 0)
  allow_empty: false            # optional: command may print nothing
```

Commands run with `bash -c` in `/work` without stdin, so they must be
non-interactive. Mark commands whose output changes between runs (`ps`,
`date`, `uptime`, `free`, `df`, anything printing ctimes/atimes) as
`deterministic: false`. If a command does not work against the seed, change
the command or the seed — never the sandbox restrictions.

After adding or changing commands in the embedded catalog:

```sh
go build -o shast .
./shast verify --id my-new-command     # try it
./shast expected                       # regenerate internal/catalog/expected/
go build -o shast . && ./shast verify  # everything passes, twice per session
```

### Without rebuilding

`--catalog DIR` loads `DIR/commands.yaml` (and optional `DIR/expected/<id>.txt`)
on top of the built-in catalog: entries with a new ID are added, entries with
an existing ID replace the built-in one. It works for `play`, `verify` and
`expected`:

```sh
./shast --catalog ~/my-commands
./shast verify --catalog ~/my-commands
./shast expected --catalog ~/my-commands --out ~/my-commands/expected
```

## Verification and determinism

- `shast verify [--runs 2] [--id X]` runs every catalog command in `--runs`
  fresh sessions, twice per session (which also checks the reset), at a fixed
  80x24 terminal. It checks the exit code, that the output is not empty and,
  for deterministic commands, that all outputs are identical after
  normalization and equal to `internal/catalog/expected/<id>.txt`. It prints
  a PASS/FAIL table and exits with 1 on any failure.
- `shast expected [--out DIR]` writes the normalized output of every
  deterministic command (default `internal/catalog/expected`) and removes
  stale files there.
- Normalization (`internal/outcmp`) strips ANSI sequences and control
  characters, converts CRLF, applies carriage-return overwrites, trims
  trailing whitespace and trailing blank lines; `ignore_order` compares lines
  as a multiset.
- The seed manifest (`/seed.sha256` in the image: path, mode, size, mtime and
  sha256 of every file) is compared with the committed
  `internal/sandbox/testdata/seed.sha256` by the tests.
  `make seed-determinism` builds the image twice without cache and compares
  the manifests (slow, needs network).
- Tool versions are pinned too: the base image is pinned by digest and apt
  installs from the matching snapshot.debian.org date, so expected outputs
  stay valid for an image tag.

## Mode 2: Reverse Challenge (not playable yet)

In Mode 2 the player sees an expected output and writes *any* command that
produces it. The groundwork is in place:

- `engine.Mode` abstracts over modes; `engine.Reverse` implements the rules:
  only deterministic challenges with a stored expected output are eligible,
  the prompt is the expected output, any non-blank input can be submitted,
  and the result is judged by comparing the normalized output with
  `outcmp.Equal` (respecting `ignore_order`).
- Expected outputs are generated from the sandbox (`shast expected`) and
  verified (`shast verify`), always at the fixed 80x24 size.

What is missing is the UI: the setup screen shows the mode as "coming soon".
It needs a free-text input screen (instead of the per-character target
display) that shows the expected output, runs the submitted command with
`sandbox.FixedSize()` and shows the verdict, plus a scoring rule for it.

## Development

```sh
make check        # gofmt, go vet, staticcheck, go test ./...
make test-short   # unit tests only
```

Integration tests talk to Docker and skip automatically without a daemon or
the image (and with `-short`).

CI (`.github/workflows/ci.yml`) runs `go vet` and `go test -race -short` on
Linux, macOS and Windows for every push and pull request. Pushing a tag `v*`
additionally creates a GitHub release with binaries for Linux, macOS and
Windows (amd64 and arm64) and a `checksums.txt`, once the tests pass.
`shast -version` prints the tag for release builds, the Go module version
from the build info otherwise, and `dev` as a last resort.

The layout follows the Go module layout guide:

```
main.go, cmd_*.go     subcommands: play (default), verify, expected, image build
internal/outcmp       output normalization and comparison
internal/catalog      challenge types, YAML loading, validation, filters (+ embedded catalog)
internal/typing       per-keystroke typing state
internal/score        WPM/accuracy statistics, highscore store
internal/engine       modes (Speed, Reverse stub), challenge selection, round lifecycle
internal/sandbox      image build (embedded context), session container, reset, run
internal/verify       catalog verification and expected-output generation
internal/tui          Bubble Tea UI: setup, rounds, summary, TTY output renderer
```
