# Task: Build a terminal-based shell command typing game in Go

## Goal
Build a CLI/TUI game that runs directly in the user's terminal. The player types
real, useful Linux shell commands as fast and accurately as possible. Once a command
is typed correctly, it is executed inside an isolated Docker container and its output
is streamed live into the TUI, exactly like a real terminal would show it.

The game has two modes sharing one engine:
- **Mode 1 – Speed Typing (implement now):** show a command, the player types it, and
  on exact match + Enter it runs in the sandbox with the output streaming in real time.
- **Mode 2 – Reverse Challenge (do NOT implement, but design for it):** show an
  expected output, the player writes any command that produces it, the command runs in
  the sandbox and its output is compared against a stored expected output.

Every architectural decision must keep Mode 2 cheap to add later.

## Language & guidelines
- Go (latest stable), shipped as a single binary.
- Follow the official Go guidelines and idioms: Effective Go, Go Code Review Comments,
  and the official module layout guide (go.dev/doc/modules/layout). Keep it simple:
  small interfaces defined where they're used, explicit error handling with wrapping,
  context for cancellation/timeouts, no premature abstraction, no frameworks for the
  sake of it.
- Choose well-maintained libraries (e.g. for the TUI and the Docker API) and briefly
  justify your choices in the plan.
- Code must pass `go vet`, `gofmt` and `staticcheck`.

## Sandbox (non-negotiable)
- Commands run inside a Docker container built from a Debian-slim based image with the
  usual CLI tools a DevOps engineer uses (coreutils, find, grep, sed, awk, jq, tar,
  git, procps, tree, ...).
- Isolation: no network, non-root user, all capabilities dropped, no privilege
  escalation, limits on PIDs, memory, CPU, per-command timeout and output size.
- The container's workspace is reset to a pristine seed state before every command,
  so destructive commands (`rm`, `find -delete`, `sed -i`, ...) are safe and
  results are reproducible.
- The container is always cleaned up, including on Ctrl+C and crashes.
- Output is streamed live with a TTY so it looks like a real terminal.
- Never weaken these restrictions to make a command work; change the command or the
  seed data instead.

## Determinism (required for Mode 2)
- The seed filesystem is a small, realistic fake project/server environment (logs,
  configs, CSV/JSON data, a small git repo, files with varied sizes, dates and
  permissions), generated by a deterministic script.
- Fixed timezone, locale, hostname, user, file mtimes and contents. No randomness.
- Commands whose output is inherently non-deterministic (`ps`, `date`, `uptime`, ...)
  are allowed in Mode 1 but must be marked so Mode 2 can exclude them.
- Provide a way to verify that every command in the catalog actually works against the
  seed data and produces identical output across fresh runs.

## Command catalog
- At least 60 real-world commands a DevOps/backend engineer actually uses: pipes,
  `xargs`, `awk`, `sed`, `sort | uniq -c | sort -rn`, `jq`, `tar`, `find -exec`,
  `grep -rn`, `chmod`, `du -sh`, `git log`, etc.
- Each command has a category, a difficulty and a short explanation shown after
  execution. Adding new commands must not require code changes.

## Mode 1 gameplay
- A session consists of multiple rounds, filterable by difficulty and category.
- Per-character feedback while typing (correct / wrong / pending). Enter only submits
  on exact match. Timer starts on the first keystroke.
- After submit: run the command, stream the output live into a scrollable area, show
  exit code, execution time and the explanation, then continue to the next command.
- Track WPM, accuracy, errors and time per round and per session; persist highscores locally.
- Must work well at 80x24, handle terminal resize, and fail with a clear message if
  Docker isn't available or the image is missing.

## Mode 2 preparation
- The engine abstracts over "modes" and "challenges" so that a challenge can carry
  either a target command or an expected output.
- Output comparison (ANSI stripping, whitespace/line ending normalization, optional
  order-insensitive compare) is implemented and tested now, and used for the catalog
  verification.
- Expected outputs for deterministic commands can be generated from the sandbox.
- Mode 2 itself is left as a documented stub.

## Quality
- Table-driven unit tests for typing logic, scoring, catalog loading and output
  comparison; integration tests for the sandbox that skip automatically without Docker.
- README with prerequisites, build/run instructions and how to add commands.
